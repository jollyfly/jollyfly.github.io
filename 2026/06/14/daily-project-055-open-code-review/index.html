定位 阿里集团官方 AI 代码评审 CLI 工具，混合架构：确定性工程 × LLM Agent

项目描述： Open-source & free — Battle-tested at Alibaba’s scale. Hybrid architecture code review tool: deterministic pipelines + LLM Agent, precise line-level comments, built-in fine-tuned ruleset (NPE, thread-safety, XSS, SQL injection), OpenAI & Anthropic compatible.

这是一个从阿里巴巴集团内部孵化出来的开源项目，历经两年多、服务的开发者数量级的生产验证，累计发现数百万个代码缺陷后开源给社区。项目用 Go 语言实现，核心哲学是：确定性工程做硬约束，LLM Agent 做动态决策，两者各司其职。

核心问题：通用 Agent 做代码评审的三大痛点

作者在 README 中直击痛点：

  1. 覆盖不全（Incomplete coverage） — 大规模 changeset 下，Agent “走捷径”，选择性忽略部分文件
  2. 位置漂移（Position drift） — 报告的问题和实际代码位置不匹配，行号或文件引用偏移
  3. 质量不稳定（Unstable quality） — 纯语言驱动的 Skills 难以调试，评审质量随 prompt 微调而大幅波动

根因分析：纯语言驱动的架构缺乏对评审过程的硬约束。

核心架构：Deterministic × Agent 混合

这是整个项目最值得学习的架构设计思想：

确定性工程 — 硬约束

模块 职责
精确文件选择 精确决定哪些文件需要评审、哪些需要过滤，确保不遗漏重要变更
智能文件打包 将关联文件打包成一个评审单元（如 message_en.properties + message_zh.properties），每个 bundle 作为独立子 Agent 运行，大规模 changeset 下稳定，支持并发评审
细粒度规则匹配 根据每个文件的特征匹配评审规则，保持模型注意力聚焦，从源头消除信息噪音
外部定位和反思模块 独立的评论定位（Re-location）+ 评论反思（Reflection）模块，系统性提升 AI 反馈的位置准确性和内容准确性

Agent — 动态决策

模块 职责
场景化 Prompt 模板 针对代码评审深度优化的 Prompt 模板，提升有效性的同时降低 token 消耗
场景化工具集 从海量生产数据中提炼工具调用分布（调用频率、重复率、对调用链的影响），形成专属于代码评审的工具集，比通用 Agent 工具集更稳定可预测

架构亮点总结

  1. 混合架构思想：不是把所有事情都交给 LLM，而是用确定性工程保证”不能出错的事情一定不会出错”，用 Agent 处理”需要灵活判断的事情”。这是对”全 AI 方案”的一种理性反思。

  2. 文件打包策略（Smart Bundling）：将关联文件打包评审，避免大 changeset 下的覆盖不全问题，同时天然支持并发。

  3. 评论定位独立模块：Re-location 是一个独立模块，不是让主 Agent 顺手解决，而是专门用一次 LLM 调用处理位置修正——这体现了对”单一职责”的坚持。

  4. 异步 Comment Worker Pool：code_comment 工具的执行是异步的，不阻塞主循环，让 Agent 可以继续进行下一轮 LLM 调用，整体延迟更低。

  5. 双阈值内存压缩：60% soft / 80% warning，既避免频繁压缩，又保证不会超限。

  6. 生产级验证：不是纸上谈兵，而是服务了阿里内部数万开发者、发现数百万代码缺陷后开源的，质量有保证。
